# Launch scope and delivery order

## Fixed product direction

Public marketing discovery feeds authenticated transactions. One verified user holds independent, dated commercial, ownership, management, tenancy and scheme relationships. A Landlord self-manages their own residential rentals; an agency manages on behalf of owners. Resident, tenant and council access are not interchangeable. Separate portals use shared records and policy enforcement, not separate identity databases.

## Delivery sequence

1. Cloudflare skeleton and permanent CI: marketing/platform build, health endpoints, isolated resources, no legacy runtime.
2. Freeze the shared domain, authorization and portal definitions with numbered SQL evolution.
3. Complete marketing -> landlord signup -> property -> booking -> work order -> Staff -> ordinary report -> private client download.
4. Complete tenant invitation -> maintenance -> manager review -> ProInspect work -> completion, then guided tenancy/document workflows with restricted evidence separately verified.
5. Property Manager portfolio, team scope, import, bulk/recurring inspection and authority workflows.
6. Build strata as one domain: resident issue -> manager triage -> council recommendation/authorised outcome -> work order -> notice -> completion.
7. Commercial/asset portfolio experience using shared operational services, not residential tenancy assumptions.
8. Full Staff productivity, report-tool automation, optional Sheets projection, marketing depth and provider integrations.
9. Reviewed data import only after target workflows are proven; production acceptance and deliberate domain cutover.

Staff delivery capability is added with each external workflow, not after the portals. Real email authentication is a release dependency, not an optional cosmetic enhancement. Manual report upload provides an initial real deliverable without waiting for the specialist Report Tool.

## Explicit release controls

Each enabled workflow requires server authorization, persistence, failure handling, an observable result and automated acceptance. Schema-only modules remain disabled. A green build does not prove hosted credentials, delivery, recovery or legal-content approval.

No automatic production deployment, old resource retirement or mass historical migration. No native mobile app, general workflow engine, full strata accounting, levies, AGM administration, statutory voting, community chat or speculative integrations in the initial build.

BUILD_STATUS.md records implemented versus pending capability. DEPLOYMENT.md records environment requirements. Do not use old repository status documents as acceptance for this rebuild.
